Introducción

En un proyecto de software varias personas modifican muchos archivos al mismo tiempo: código, diagramas, documentos y pruebas. Sin un método, dos personas editan lo mismo, se pierden versiones y nadie sabe por qué se hizo un cambio. La Administración de la Configuración del Software (ACS) es la disciplina que evita ese desorden.

Según Pressman, el proceso ACS tiene cuatro objetivos:

Identificar

Todos los ítems que forman la configuración del software.

Controlar

Los cambios que se hacen a uno o más de esos ítems.

Construir

Facilitar la creación de distintas versiones de una aplicación.

Preservar

Garantizar que la calidad se mantenga mientras el software evoluciona.

¿Qué es un ICS?

Un ítem de configuración del software es cualquier producto de trabajo que se deba controlar: un módulo de código, una sección de los requerimientos o un conjunto de casos de prueba.

Desarrollo

El repositorio del proyecto

El repositorio es la base de datos donde viven todos los ICS. No solo guarda archivos: recuerda cómo se relacionan y qué les ha pasado. Estas son sus funciones principales:

Variedad de objetos

Almacena texto, gráficos, mapas de bits, documentos, código objeto, datos de prueba y resultados. Un repositorio maduro puede seguir una pieza muy pequeña o un grupo completo de módulos.

Rastreo de dependencias

Maneja las relaciones entre los elementos almacenados. Si cambia un diagrama de clases UML, detecta qué clases, interfaces y componentes podrían necesitar cambios y avisa al desarrollador.

Rastreo de requerimientos

Hacia adelante: de un requerimiento a todo lo construido a partir de él. Hacia atrás: de un producto de trabajo al requerimiento que lo originó.

Administración de configuraciones

Conserva las configuraciones que representan hitos del proyecto o liberaciones a producción.

Ensayos de auditoría

Registra cuándo, por qué y quién hizo cada cambio. Puede avisar automáticamente cuando se modifica un elemento para iniciar el registro.

El proceso ACS y sus preguntas

Un buen proceso ACS no tiene que ser burocrático ni pesado, pero sí debe permitir al equipo responder preguntas complejas:

  • ¿Cómo se identifican los elementos de la configuración?
  • ¿Cómo se manejan las muchas versiones de un programa y su documentación?
  • ¿Cómo se controlan los cambios antes y después de entregar el software al cliente?
  • ¿Quién aprueba y clasifica los cambios solicitados?
  • ¿Cómo se garantiza que los cambios se hicieron bien?
  • ¿Cómo se entera el resto del equipo de lo que cambió?

De esas preguntas salen cinco tareas: identificación, control de versión, control de cambio, auditoría de la configuración y reporte. Pressman las dibuja como capas concéntricas: los ICS nacen en el centro y avanzan hacia afuera durante su vida útil, hasta formar parte de una versión del software.

No todos los ítems pasan por todas las capas. Un ICS nuevo siempre debe identificarse, pero si nadie pide cambiarlo, la capa de control de cambio no se aplica. Se le asigna a una versión del software, y su registro (nombre, fecha de creación, versión, etc.) se conserva para auditorías y se reporta a quien necesite saberlo.

Identificación de objetos de configuración

Para controlar un ICS, primero hay que darle un nombre propio y organizarlo con un enfoque orientado a objetos. Existen dos tipos:

TipoQué esEjemplos
Objeto básicoUnidad de información creada durante el análisis, el diseño, la codificación o las pruebas.Una sección de requerimientos, el código fuente de un componente, un conjunto de casos de prueba.
Objeto agregadoColección de objetos básicos y de otros objetos agregados.Una especificación de diseño que reúne el modelo de arquitectura, el modelo de datos y varios componentes.

Cada objeto se distingue por cuatro características:

Nombre

Cadena de texto que lo identifica sin ambigüedad.

Descripción

Tipo de ICS, proyecto al que pertenece e información de cambio o versión.

Recursos

Lo que el objeto proporciona, procesa o necesita: tipos de datos, funciones, variables.

Realización

Puntero al contenido real en un objeto básico; nula en un agregado.

La identificación también registra cómo se conectan los objetos. Una relación <parte de> forma una jerarquía de ICS, y una relación <interrelacionado> une objetos de ramas distintas de esa jerarquía. Estas relaciones sirven para valorar el impacto de un cambio, pero cuestan tiempo y son difíciles de mantener al día, por eso no son esenciales para la administración global del cambio.

Además, el esquema debe aceptar que los objetos evolucionan: antes de ser línea de referencia pueden cambiar muchas veces, y después de serlo los cambios siguen ocurriendo.

Control de versión

El control de versión combina procedimientos y herramientas para manejar las distintas versiones de los objetos de configuración que se crean durante el proceso de software. Un sistema de control de versión ofrece estas capacidades:

Base de datos del proyecto

El repositorio que almacena todos los objetos de configuración relevantes.

Administración de versiones

Guarda todas las versiones de un objeto, o permite reconstruir cualquiera usando las diferencias entre versiones pasadas.

Facilidad de elaboración

Reúne todos los objetos relevantes y construye una versión específica del software.

Rastreador de conflictos

Permite registrar y seguir el estado de los problemas pendientes de cada objeto (también llamado rastreador de errores). Suele venir junto con el control de versión y de cambio.

Algunos sistemas definen un conjunto de cambio: todos los cambios, respecto a una configuración de referencia, que hacen falta para crear una versión concreta. Dart lo describe como un registro de los cambios en todos los archivos, con su razón, quién los hizo y cuándo. Así se puede construir una versión indicando por nombre qué conjuntos de cambio aplicar.

Para lograrlo se usa el modelado del sistema, cuyo modelo contiene una plantilla (jerarquía de componentes y orden de construcción), reglas de construcción y reglas de verificación. Ese modelo también sirve para valorar cómo un cambio en un componente impacta a los demás.

Herramienta: SVC (CVS)

El Sistema de Versiones Concurrentes es muy usado, nació para código fuente pero sirve para cualquier archivo de texto. 1) Crea un repositorio simple. 2) Guarda todas las versiones de un archivo en uno solo, almacenando solo las diferencias. 3) Protege contra cambios simultáneos dando a cada desarrollador su propio directorio, y mezcla los cambios cuando terminan. No es un sistema de construcción (hay que integrarlo con herramientas como Makefile) ni implanta un proceso de control de cambio. Es gratuito, de código abierto, cliente-servidor y funciona en Windows, Mac OS, Linux y Unix.

Control de cambio

James Bach resume la realidad del cambio: es vital controlarlo, pero las mismas fuerzas que lo hacen necesario lo hacen desconcertante. Un pequeño cambio en el código puede causar una gran falla, o arreglar una grande; un solo desarrollador descontrolado puede hundir un proyecto, aunque de esas mismas mentes salgan ideas brillantes, y un control agobiante podría desanimarlos a crear. Es un acto de equilibrio: demasiado control crea problemas, y muy poco también. En un proyecto grande, el cambio descontrolado lleva rápido al caos.

Por eso el control de cambio combina procedimientos humanos y herramientas automatizadas. El proceso (figura 22.5 del libro) se resume en tres etapas:

Solicitud y decisión

  1. Se reconoce la necesidad del cambio.
  2. El usuario envía la petición de cambio.
  3. El desarrollador la evalúa.
  4. Se genera el reporte de cambio.
  5. La autoridad de control de cambio (ACC) decide: si lo niega, se informa al usuario; si lo aprueba, se pone en fila y se genera la OCI.

Realización

  1. Se asignan personas a los objetos de configuración.
  2. Se hace la “salida” (check out) de los ítems.
  3. Se hace el cambio.
  4. Se revisa (audita) el cambio.
  5. Se hace la “entrada” (check in) de los ítems modificados.
  6. Se establece una línea de referencia para prueba.

Integración y entrega

  1. Se realizan actividades de calidad y pruebas.
  2. Se “promueven” los cambios para la siguiente liberación.
  3. Se reconstruye la versión adecuada.
  4. Se audita el cambio en todos los ítems.
  5. Se incluyen los cambios en la nueva versión.
  6. Se distribuye la nueva versión.

La petición de cambio se evalúa según su mérito técnico, sus posibles efectos colaterales, su impacto global sobre otros objetos y funciones del sistema, y su costo. El resultado se presenta como un reporte de cambio, y la ACC (una persona o un grupo) toma la decisión final sobre su estatus y prioridad. Por cada cambio aprobado se genera una orden de cambio de ingeniería (OCI), que describe el cambio, las restricciones y los criterios de revisión y auditoría. Varias peticiones pueden juntarse en una sola OCI, y una OCI suele afectar varios objetos de configuración.

Durante el cambio, el objeto puede ponerse en un directorio controlado solo por quienes lo modifican, o “sacarse” del repositorio, cambiarse y aplicarse las actividades de aseguramiento de calidad; luego “entra” de nuevo y el control de versión crea la siguiente versión. Este mecanismo implementa dos elementos clave de la gestión del cambio:

Control de acceso

Determina qué ingenieros pueden acceder y modificar un objeto de configuración.

Control de sincronización

Evita que cambios paralelos hechos por dos personas se sobrescriban entre sí.

Tres niveles de control

Pressman reconoce que este proceso puede parecer burocrático, y que sin salvaguardas retrasa el avance. Por eso el rigor aumenta según la madurez del ICS:

NivelCuándo se aplicaQuién aprueba
InformalAntes de que el ICS sea línea de referencia.El propio desarrollador, si el cambio está justificado y no afecta requerimientos más amplios del sistema.
A nivel de proyectoCuando el ICS ya es línea de referencia (después de revisión técnica y aprobación).El gerente del proyecto si el cambio es local; la ACC si afecta a otros ICS.
FormalCuando el software se libera a los clientes.Se sigue el procedimiento completo de la figura 22.5.

Una línea de referencia también puede crearse por otras razones. Por ejemplo, en las “construcciones diarias”, todos los componentes verificados en un momento se vuelven la referencia para el trabajo del día siguiente.

La ACC tiene un papel activo en las capas de control de versión y de cambio. Según el tamaño del proyecto puede ser una sola persona (el gerente) o un grupo con representantes de software, hardware, bases de datos, soporte y mercadotecnia. Su función es tener una visión global: ¿cómo afecta el cambio al hardware, al desempeño, a la percepción del cliente, a la calidad y a la confiabilidad?

Caso CasaSegura

Al comenzar el proyecto, el gerente Doug Miller reúne a su equipo porque mercadotecnia ya pidió “segundas opiniones”. Recuerdan que en un proyecto anterior los cambios incontrolados causaron muchas demoras. Doug propone tres cosas: 1) desarrollar o adoptar un proceso de control de cambio (cómo se solicitan, evalúan y registran los cambios), 2) conseguir una buena herramienta ACS para control de cambios y versiones, y 3) que todos se comprometan a seguir el proceso y a usar las herramientas.

Auditoría de configuración

La identificación, el control de versión y el control de cambio mantienen el orden, pero incluso los mejores mecanismos solo rastrean un cambio hasta que se genera la OCI. Para asegurar que se implementó bien hacen falta dos cosas: revisiones técnicas y auditoría de la configuración.

La revisión técnica se enfoca en la exactitud técnica del objeto modificado: su consistencia con otros ICS, omisiones y posibles efectos colaterales. Debe hacerse para todos los cambios, salvo los más triviales. La auditoría la complementa evaluando lo que normalmente no se ve en la revisión, y responde seis preguntas:

  • ¿Se hizo el cambio especificado en la OCI? ¿Se agregó alguna modificación extra?
  • ¿Se hizo una revisión técnica para valorar su exactitud?
  • ¿Se siguió el proceso y se aplicaron los estándares de ingeniería de software?
  • ¿Se destacó el cambio en el ICS, con fecha y autor, y los atributos del objeto lo reflejan?
  • ¿Se siguieron los procedimientos ACS para anotar, registrar y reportar el cambio?
  • ¿Se actualizaron correctamente los ICS relacionados?

A veces estas preguntas se plantean dentro de la revisión técnica. Pero cuando la ACS es una actividad formal, la auditoría la realiza por separado el grupo de aseguramiento de calidad, que además comprueba que los ICS correctos (por versión) entren en cada construcción y que la documentación esté actualizada y sea consistente con la versión construida.

Reporte de estado

El reporte del estado de la configuración (a veces llamado contabilidad de estado) responde cuatro preguntas: ¿qué ocurrió? ¿quién lo hizo? ¿cuándo? ¿qué más se verá afectado?

Se hace una entrada de reporte cada vez que a un ICS se le asigna una nueva identificación o se actualiza, cada vez que la ACC aprueba un cambio (emite una OCI) y cada vez que se realiza una auditoría, cuyos resultados también se reportan. La salida puede publicarse en una base de datos en línea o en un sitio web, donde desarrolladores y personal de apoyo la consultan por palabras clave. Además se genera un reporte periódico para mantener al tanto de los cambios importantes a gerentes y profesionales.

Consejo del libro: mantener una lista de “se necesita saber” para cada objeto de configuración, y avisar a todos los de la lista cada vez que haya un cambio.

Las herramientas ACS apoyan una o más actividades del proceso. La mayoría de las modernas trabajan junto con un repositorio (un sistema de base de datos) y ofrecen mecanismos para identificación, control de versión y de cambio, auditoría y reportes. ACS para webapps

Las webapps se diferencian del software tradicional por la naturaleza siempre presente del cambio. Sus desarrolladores suelen usar un modelo iterativo e incremental con principios del desarrollo ágil: el equipo entrega un incremento en muy poco tiempo, guiado por el cliente, y los incrementos posteriores agregan contenido y funcionalidad. Por eso la pregunta que plantea el libro es qué impacto tiene el cambio descontrolado sobre una webapp. El fragmento revisado termina aquí, al inicio de esta sección.

Las tareas ACS aplicadas con Git y GitHub

El trabajo en equipo de este proyecto pone en práctica cada tarea del proceso:

Tarea ACSEquivalente en Git y GitHub
RepositorioEl repositorio de GitHub, que guarda todos los archivos y su historial.
IdentificaciónNombres de archivos y carpetas, y el identificador único de cada commit.
Control de versiónCommits y ramas (branches): cada integrante trabaja aislado en su rama.
Control de cambioLos Pull Requests: se propone el cambio, se revisa y se aprueba antes de integrarlo a main.
AuditoríaLa revisión del Pull Request y la comprobación de que el cambio hace lo que dice.
Reporte de estadoEl historial de commits (git log), que dice qué cambió, quién y cuándo.

Conclusión

La ACS convierte el cambio, que en un proyecto es inevitable, en algo ordenado y rastreable. Todo empieza por identificar cada ítem; después el control de versión guarda su historia, el control de cambio decide qué se modifica y quién lo aprueba, la auditoría comprueba que se hizo bien y el reporte mantiene informado a todo el equipo.

El mensaje central del capítulo es el equilibrio: sin control el proyecto cae en el caos, y con demasiada burocracia se frena el trabajo. Herramientas como Git y GitHub ponen en práctica estas ideas y permiten aplicarlas sin hacer el proceso pesado.
