Repositorio, proceso ACS e identificación de objetos de configuración · Administración de la Configuración del Software (Pressman, cap. 22).

Introducción Desarrollo Ejemplos Conclusión

Introducción

En un proyecto de software participan varias personas que modifican muchos archivos al mismo tiempo: código, diagramas, documentos y pruebas. Sin un método para ordenar ese trabajo, es fácil que dos personas editen lo mismo, que se pierda una versión o que nadie sepa por qué se hizo un cambio. La Administración de la Configuración del Software (ACS) es la disciplina que evita ese desorden.

Pressman explica que el proceso ACS persigue cuatro objetivos: identificar todos los ítems que forman la configuración del software, controlar los cambios que se les hacen, facilitar la construcción de distintas versiones de una aplicación y asegurar que la calidad no se pierda mientras el software evoluciona.

A cada uno de esos ítems se le llama ICS (ítem de configuración del software): cualquier producto de trabajo que se deba controlar, como un módulo de código, una sección de los requerimientos o un conjunto de casos de prueba.

Desarrollo

El repositorio del proyecto

El repositorio es la base de datos donde viven todos los ICS. No solo guarda archivos: también recuerda cómo se relacionan entre sí y qué les ha pasado. Pressman destaca estas funciones:

  • Variedad de objetos: almacena texto, gráficos, código, datos de prueba y resultados. Un repositorio maduro puede seguir la pista a una pieza muy pequeña (una definición de datos) o a un grupo completo de módulos.
  • Rastreo de dependencias: sabe qué elementos dependen de cuáles. Si se modifica un diagrama de clases, avisa que las clases, interfaces y componentes relacionados quizá también deban cambiar.
  • Rastreo de requerimientos: permite ir hacia adelante (de un requerimiento a todo lo que se construyó a partir de él) y hacia atrás (de un producto de trabajo al requerimiento que lo originó).
  • Administración de configuraciones: conserva las configuraciones que representan hitos del proyecto o entregas a producción.
  • Ensayos de auditoría: registra cuándo, por qué y quién hizo cada cambio.

Las preguntas que debe responder el proceso ACS

Un buen proceso ACS no tiene que ser burocrático, pero sí debe permitir al equipo responder preguntas como estas:

  • ¿Cómo se identifican los elementos que componen la configuración?
  • ¿Cómo se manejan las muchas versiones de un programa y su documentación?
  • ¿Cómo se controlan los cambios antes y después de entregar el software al cliente?
  • ¿Quién aprueba y clasifica los cambios solicitados?
  • ¿Cómo se comprueba que el cambio se hizo bien?
  • ¿Cómo se informa a los demás de lo que cambió?

Las cinco tareas: un modelo de capas

De esas preguntas salen cinco tareas: identificación, control de versión, control de cambio, auditoría de la configuración y reporte. Pressman las dibuja como capas concéntricas. Los ICS nacen en el centro y avanzan hacia afuera durante su vida útil, hasta formar parte de una versión del software.

No todos los ítems pasan por todas las capas. Un ICS recién creado siempre debe identificarse, pero si nadie pide cambiarlo, la capa de control de cambio simplemente no se aplica. Los compañeros desarrollan en sus apartados las capas de versión, cambio, auditoría y reporte; aquí me concentro en la primera.

Identificación de objetos de configuración

Para poder controlar un ICS, primero hay que darle un nombre propio y organizarlo con un enfoque orientado a objetos. Existen dos tipos:

TipoQué esEjemplos
Objeto básicoUnidad de información creada durante el análisis, el diseño, la codificación o las pruebas.Una sección de requerimientos, el código fuente de un componente, un conjunto de casos de prueba.
Objeto agregadoColección de objetos básicos y de otros objetos agregados.Una especificación de diseño que reúne el modelo de arquitectura, el modelo de datos y varios componentes.

Cada objeto se distingue por cuatro características:

  • Nombre: una cadena de texto que lo identifica sin ambigüedad.
  • Descripción: el tipo de ICS que es (modelo, programa, datos), el proyecto al que pertenece y su información de cambio o versión.
  • Recursos: las entidades que el objeto proporciona, procesa o necesita, como tipos de datos, funciones o nombres de variables.
  • Realización: un puntero al contenido real en el caso de un objeto básico; en un objeto agregado es nula.

Relaciones entre objetos

La identificación también registra cómo se conectan los objetos. Una relación de pertenencia (<parte de>) forma una jerarquía de ICS, mientras que una relación <interrelacionado> une objetos de ramas distintas de esa jerarquía. Estas relaciones sirven para analizar el impacto de un cambio, pero cuestan tiempo y son difíciles de mantener al día, por eso no siempre son indispensables.

Además, el esquema de identificación debe aceptar que los objetos evolucionan. Antes de convertirse en línea de referencia un objeto puede cambiar muchas veces, y después de serlo los cambios siguen ocurriendo, aunque con más control.

Ejemplos

Ejemplo del libro: una especificación de diseño

Una DesignSpecification es un objeto agregado: funciona como una lista nombrada de punteros hacia otros objetos.

DesignSpecification        (objeto agregado)
          ├── ArchitecturalModel     (objeto agregado)
          ├── DataModel              (objeto agregado)
          ├── ComponentN             (objeto básico)
          └── UMLClassDiagramN       (objeto básico)

Con la notación de relaciones se expresa así:

Diagrama clase        <parte de>         Modelo requerimientos
          Modelo requerimientos <parte de>         Especificación requerimientos
          ModeloDatos           <interrelacionado> CasoPruebaClaseM

Ejemplo en este mismo proyecto

Nuestra página web también tiene ICS. Cada archivo es un objeto básico con nombre propio, y el sitio completo es el objeto agregado que los reúne.

Sitio Línea Base           (objeto agregado)
          ├── index.html             (objeto básico)
          ├── html/ramon.html        (objeto básico)
          ├── assets/css/styles.css  (objeto básico)
          └── scripts/script.js      (objeto básico)

Si cambia styles.css, la relación de dependencia nos dice que index.html y las páginas de resumen podrían verse afectadas, y por eso conviene revisarlas. Git y GitHub hacen de repositorio: guardan cada objeto, quién lo modificó y cuándo.

Conclusión

La ACS convierte el cambio, que en un proyecto es inevitable, en algo ordenado y rastreable. Todo empieza por la identificación: lo que no tiene nombre ni descripción no se puede controlar. El repositorio mantiene los ICS y sus relaciones, y el proceso de cinco capas guía cada ítem desde que se crea hasta que forma parte de una versión del software.

Entender estos fundamentos permite ver por qué herramientas como Git no son un lujo: ponen en práctica la identificación, el versionado y el registro de cambios que Pressman describe.
